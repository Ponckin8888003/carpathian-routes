# Сценарій демонстрації курсової «Карпатські маршрути»

Потреба користувача: турист хоче вибрати вершину й зберегти план походу, а потім його
змінити або видалити.

## Підготовка

1. `npm install`, `npm run build`, `npm run preview` → http://localhost:4173.
2. Початкові демонстраційні плани: `plan-001` (Говерла) і `plan-002` (Бребенескул).
   Щоб почати спочатку, видаліть у DevTools → Application → Local Storage ключ
   `carpathian.plans.v1` лише для цієї адреси.
3. Режим даних — mock (localStorage). Це автономний режим, не реальний сервер.

## Хід показу (5–7 хвилин)

1. Головна: призначення сервісу. Каталог `/peaks`: пошук, фільтр «Лише з маршрутами».
2. Сторінка вершини `/peaks/hoverla` → «Вибрати й підготувати план походу».
3. Некоректна спроба: порожня форма → пояснення, фокус на першому полі. Тривалість 5 днів
   без поради → помилка зв’язку полів.
4. Виправити поля, створити план → сторінка `/plans/{id}`, повідомлення «План створено.».
5. «Редагувати»: змінити нотатки → збережено, той самий `id`.
6. Список `/plans`: пошук, фільтр поради, сортування; порожній результат й «Скинути умови».
7. «Видалити»: спершу скасувати, потім підтвердити видалення створеного плану.
8. Перезавантажити сторінку: зміни збереглися. Відкрити `/plans/missing` і `/unknown`.
9. Тести: `npm run test:run`; пояснити межу — підмінено лише `planService`.
10. Вимірювання продуктивності (таблиця в `project-plan.md`) і відомі обмеження.

## Межі рішення

- Дані тільки локальні; REST-адаптер перевірено лише тестами з підміною `fetch`.
- План не є підтвердженим бронюванням; карта Mapy.com ще не підключена.
- Дані між `localhost:5173` і `localhost:4173` не спільні (різні origin).
- На хостингу потрібне правило повернення `index.html` для клієнтських маршрутів.
